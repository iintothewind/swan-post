## 回帖内容

个人理解的,agent设计上 工具能力的优先级排序，

**我的排序：build-in tools > Skills > CLI > MCP**

几个理由：

**1. build-in tools 理应最高优先级**

Agent 的 built-in tools 是它的「母语」—— 调用约定、返回值结构、错误处理全是原生默契。如果 built-in tools 在性能、token 效率或可操作性上不如外部方案，那该反省的是 Agent 本身的实现质量。作为使用者，如果发现一个 Agent 的 native tool 能力弱到需要频繁绕道外部工具，可能该考虑换个 Agent 了。当然长尾领域不可能全部覆盖，这是现实限制，但当 native tool 能覆盖时，优先用它。

**2. Skills > CLI**

Skill 本质上是经过提纯和定制的 CLI 能力 —— 把 CLI 用法、参数说明、输出格式、注意事项打包成一个按需加载的 markdown 文件。它比裸 CLI 多了「怎么用」的说明，Agent 读一次就知道怎么调，不需要试错。所以它优先于 CLI。

**3. CLI > MCP**

CLI 虽然不完美 —— 非结构化输出需要 Agent 自己 parse、管道链组合对模型推理能力要求高、交互式 CLI 基本不可用 —— 但至少轻量，不需要常驻进程。MCP 的问题在于：
- 全量 schema 灌进 prompt，上下文膨胀
- 需要后台维持 server 进程/连接
- 很多时候你只想要一个 tool，但一装就是一整组

MCP 的理论优势是标准化和动态发现，实际代价偏高。

**CLI 内部也有分化**：带 `--json` 输出的 CLI 接近 MCP 的结构化程度；管道链组合对模型是认知负担，因为没有类型检查的「胶水代码」；交互式 CLI 基本跟 Agent 无缘。

**MCP 不算完全鸡肋**，有一个 Skills 和裸 CLI 都做不到的事：返回结构化类型数据，Agent 不需要从文本里 regex 提取结果。但它的适用场景更偏向「动态变化的数据源」（实时 API、数据库查询），而 Skills 更适合「静态固定的操作」（特定 CLI 工具的用法）。两者场景不完全重叠。
