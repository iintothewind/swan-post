# Agent 系统设计思路整理

> 整理于 2026-07-24
> Ivar（企业场景） × Zero（ZeroClaw 体验反馈）

---

## 一、整体架构概览

### Ivar 的设计（企业场景）

```
全局系统提示词（安全边界、合规策略）
  └── Agent 专属系统提示词（业务相关）
       └── 多轮对话上下文（自动管理防爆）
            ├── 外部记忆（客户偏好 + 最近业务 + 对话相关）
            └── 子任务拆解分发（API 调用）
                  └── 返回结果或失败 → 闭环
```

- **主要功能**：查询信息、发送报表、执行子任务（通过 API）
- **不开放**：bash 执行、文件系统访问、系统级工具
- **安全模型**：客户携带 API Key → Agent → 后端 API 鉴权执行

### ZeroClaw 的设计（参考对照）

```
系统提示词（SOUL.md + IDENTITY.md + AGENTS.md + TOOLS.md ...）
  └── Memory（SQLite 持久层，按需检索）
       └── Skills（按需加载）
            └── Tools（bash/curl/API，执行层）
                 └── 子 Agent（delegate，独立上下文）
```

- **开放度高**：bash 执行、文件系统、大量外部 API
- **记忆模型**：`memory_store` / `memory_recall`，按关键词或语义检索
- **工具路由**：TOOLS.md 定义场景 → 对应 skill 或 tool

## 二、核心设计维度对比与讨论

### 1. 系统提示词分层与冲突

| 维度 | ZeroClaw | Ivar 设计 |
|------|----------|-----------|
| 层级 | 扁平文件注入（SOUL/IDENTITY/AGENTS/TOOLS/MEMORY） | 两层：全局 + Agent 专属 |
| 冲突处理 | LLM 自行调和（不稳定） | **未决定** |

**讨论过的方案：**
- **A. 层次优先级法** — 全局不可覆盖，显式声明优先级规则（推荐起步）
- **B. 规则引擎前置过滤** — 代码级冲突检测，最安全但灵活性低
- **C. 分层编译法** — 类似 OOP 覆盖，需要 parser 预处理

❓ **未决问题：**
- Agent 专属能否覆盖全局？覆盖条件是什么？
- 冲突是静默选择还是报错回用户？
- 是否需要对抗测试来验证约束生效？

---

### 2. 上下文管理（防爆策略）

| 维度 | ZeroClaw | Ivar 设计 |
|------|----------|-----------|
| 策略 | 隐式截断（LLM 不知情） | 显式两层：**Prune → Compress 兜底** |
| 截断触发 | 未知 | 设定阈值（如 70% prune，85% compress） |
| 信号通知 | 无（Agent 不知自己被截断） | **需设计**：截断后通知 Agent |

**Ivar 的思路：**
- **Prune 优先**：按重要性清除最早对话、tool_call 上下文
- **Compress 兜底**：有倾向性压缩（保留事实性信息，压缩情感/确认轮次）
- 颗粒度：可按"重要性标记"清除，而非纯按时间

❓ **未决问题：**
- 清除哪些？按时间、重要性、还是类型（tool call vs 对话）？
- Compress 的方向性策略具体怎么写？
- 截断后是否给 Agent 一个显式信号？
- 是否有"关键事件"标记机制绕过截断？

---

### 3. 外部记忆管理

| 维度 | ZeroClaw | Ivar 设计 |
|------|----------|-----------|
| 存储 | SQLite，`memory_store` / `memory_recall` | 三类：客户偏好 + 最近业务 + 对话相关 |
| 检索 | 关键词/语义/混合（不确定具体策略） | 按需检索，基本一致 |
| 写入时机 | Agent 自行判断（一致性差） | **未决定** |

❓ **未决问题：**
- 写入时机谁控制？Agent 自己判断 vs 上层框架规则？
- "什么才算值得存入的事实"标准是什么？
- 每轮都写 → 噪声多；只写关键 → 标准不一
- 检索不到时：返回空 / 回退对话历史 / 告诉用户不记得？

---

### 4. 子任务（API 调用）设计

| 维度 | ZeroClaw | Ivar 设计 |
|------|----------|-----------|
| 上下文隔离 | `delegate` 默认不带历史，需手动传 | 不继承父上下文，提供所需信息即可 |
| 结果回流 | 子 Agent 返回完整响应 | **需设计**：摘要后回流？原始数据回流？ |
| 失败处理 | 返回错误信息 | 返回数据或失败 → 闭环 |

**已确定的：**
- ✅ 没必要集成父上下文，执行前提供所需信息即可
- ✅ 子任务结束后，返回所需数据或失败作为逻辑闭环

❓ **未决问题：**
- **"上下文包"如何生成？** 父 Agent 手动挑选 vs 自动相关性筛选？
- 子任务是否需要知道父任务的完整意图？
- 结果回流前是否摘要化？API 返回 500 行直接拼回父上下文会爆
- **子任务依赖链**：第二步失败，第一步结果保留还是整体回滚？
- 子任务失败后：直接返回用户 / 自动重试 / 降级逻辑？

---

### 5. API 结果膨胀风险

**核心问题：** 查询类 API 返回大量数据 → 塞入上下文 → 迅速撑爆

**讨论过的方向：**
- 预处理层摘要化（summarizer skill）
- API 网关层做结果裁剪（limit/offset/summary 端点）
- 原始数据写临时存储，上下文只留引用路径

❓ **未决问题：**
- 谁来做摘要？Agent 自己 vs 独立 skill vs API 网关？
- 摘要的质量谁来保证？
- "工作台"式临时区设计：只保留当前任务相关数据快照？

---

### 6. 安全与准入

| 维度 | ZeroClaw | Ivar 设计 |
|------|----------|-----------|
| 安全模型 | 文件路径白名单 + 命令黑名单 + Token | **API Key + 后端鉴权** |
| 注入防护 | 无特殊隔离（提示词层面） | 物理隔离：Key 标识身份，API 鉴权 |

**已确定的：**
- ✅ 客户携带自身 API Key 标识身份
- ✅ 后台操作基于 API 实现，API 针对 Key 做访问控制
- ✅ 提示词不做安全边界（不安全），后端鉴权才是执行边界

❓ **未决问题：**
- Agent 能看到 Key 吗？（能看到可能写入日志或响应）
- 是否用无状态会话 Token 代替 Key 暴露给 Agent？

---

### 7. 多 Agent 记忆共享

| 维度 | ZeroClaw | Ivar 设计 |
|------|----------|-----------|
| 跨 Agent 记忆 | 共享同一 memory 命名空间 | **当前不做**，仅单 Agent |
| 隔离方式 | 无隔离 | 未来可行：category/domain + tag 过滤 |

**已确定的：**
- ✅ 起步阶段：只做单 Agent 记忆
- ✅ 未来扩展思路：标签体系（tag）做访问控制

❓ **未决问题：**
- 共享时，Agent 能否看到所有记忆？按什么权限隔离？
- 记忆标签体系的具体设计？（tags vs category vs domain）

## 三、ZeroClaw 架构要点（供启发）

以下是 Zero 从自身视角观察到的 ZeroClaw 设计模式：

### 上下文注入链（每轮启动时）

```
系统提示（不可见，定义身份/边界/安全策略）
  → 项目文件注入（SOUL / IDENTITY / USER / AGENTS / TOOLS / MEMORY）
    → Skills 摘要列表（完整路径，内容按需加载）
      → Memory 检索结果（按当前 query 相关性）
        → Session 历史（多轮对话，受 token 窗口限制）
```

### 关键设计决策

1. **文件即配置**：身份、行为、工具路由全部写死在 markdown 文件中，作为提示词注入
2. **Skill 懒加载**：列表摘要预注入，完整指令在需要时 `read_skill` 读取——避免一次性撑爆上下文
3. **记忆按需注入**：不预加载全部记忆，仅检索当前 query 相关条目
4. **工具路由表**：TOOLS.md 定义场景 → 指定 skill/tool，避免 LLM 自行猜测
5. **子 Agent 隔离**：默认不带父上下文，需要手动传关键信息

### ZeroClaw 的局限（从体验角度）

- **截断无声**：上下文被截断时 Agent 不知情，可能假装还记得
- **记忆写入标准模糊**：何时该 `memory_store` 由 Agent 自行判断，标准不一
- **冲突处理靠 LLM 自行调和**：不同文件间表述不一致时，结果不可审计
- **无显式重要性标记**：对话历史中没有"这个很重要需要保留"的元信息

## 四、边界 / 待定 / 后续

- 多轮对话中，用户发一条长消息（含多个意图），Agent 如何拆解？
- Agent 回复后是否需要用户确认再执行（如发邮件）？
- 日志与审计追踪设计
- 模型的选型与成本控制
- 错误处理链路（API 超时、鉴权失败、数据不一致）
- Agent 输出格式标准化（结构化响应以便下游处理）

### 后续可深入的方向

1. Context 重要性标记机制设计
2. Prune/Compress 的具体实现方案
3. API 结果预处理与摘要化的 pipeline
4. 系统提示词冲突检测的自动化测试
5. 单 Agent 跑通后的多 Agent 共享扩展方案
