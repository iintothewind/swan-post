# omp 上下文压缩实战：snapcompact 到底省了什么、又贵在哪里

> 写给我自己和其他在长会话里被 context window 卡住的人。客观论述，只讲我实测和读源码得到的。
> 实测对象：omp（`oh-my-pi`）的 `snapcompact`。数据来自一个真实样本会话 + `oh-my-pi` 源码，已脱敏。

## TL;DR

**一句话：snapcompact 把旧对话渲染成紧凑的黑白位图（PNG），交给能"看"图片的视觉模型当图片喂回去，从而把历史按 ~1/3 的 token 代价存进上下文窗口。它省的是 context window，不是墙钟速度——代价是打爆前缀缓存，压缩后首次响应变慢。**

- **省多少**：实测样本 `tokensBefore 113132 → tokensAfter 37076`（÷3.05，省 67%）
- **怎么省**：把 79946 字符压成 4 张 196×71 的黑白图，每张 ~1–1.4 万字符
- **代价**：要视觉模型；改上下文（文本→图）会失效前缀缓存，首响应变慢；视觉 token 比文本贵
- **对比文字有损摘要（soft）**：soft 更省 token 但丢信息；snapcompact 保真度高、但"省"的方向不同

## 什么是 snapcompact

长会话里，旧历史会占满 context window。传统做法是**有损摘要**：让 LLM 把旧对话总结成一段散文。snapcompact 走了一条完全不同的路——**不写文字，而是把旧对话"截图"**：

1. 把历史文本用**像素字体**排成黑白位图（PNG），像老式终端截图。
2. 把这些图作为**图片附件**塞进下一次请求，交给**视觉模型**去"看"。
3. 图里保留的是逐字级别的文本，所以保真度远高于散文摘要。

作者是 can1357（oh-my-pi 作者），omp 默认启用。关键：**它是本地渲染，不经过任何 LLM/API/网络**——渲染在本地 Rust 里完成，没有外部调用。

## 一个真实样本的数据

我从一个真实会话文件里抓到一条完整的 snapcompact 记录（已脱敏）：

```
method:      snapcompact
tokensBefore: 113132
tokensAfter:  37076      # ÷3.05，省 67%
totalChars:  79946 字符被归档
frames:      4 张
```

帧的元数据：

```
frame[0]: 196×71,  13894 chars, font=8x13, variant=bw, detail=original
frame[1]: 196×71,  13916 chars, font=8x13, variant=bw, detail=original
frame[2]: 196×71,  13916 chars, font=8x13, variant=bw, detail=original
frame[3]: 196×71,  10387 chars, font=8x13, variant=bw, detail=original
```

摘要部分（compaction summary）只是简短的 resume lead-in + 文件操作列表，例如：

> "Resume prior conversation. Earlier turns archived under HISTORY below, oldest→newest. Read HISTORY fully; continue the live conversation follow…"

也就是说：**上下文里旧历史 = 4 张图 + 一小段摘要文字**，模型能"读图"还原出几乎逐字的历史。

帧在会话文件里**不是内联 base64**，而是存成 `blob:sha256:...` 引用（76 字符）。真正的 PNG 单独存 blob store，用到时惰性读取——这个设计我后面说。

## 跟文字有损摘要（soft）比

两者都压缩旧历史，但方向相反：

| 维度 | **snapcompact（图）** | **soft（文字摘要）** |
|---|---|---|
| 原理 | 本地渲染位图，模型"看图" | LLM 调用，把历史总结成散文 |
| 保真度 | **高**（逐字级，F1 实测 0.80–0.88） | **低**（散文摘要 F1 约 0.25–0.89） |
| 省 token | 归档部分 ~1/3 价 | **可能更省**（摘要可极端精简） |
| 压缩动作本身 | 本地渲染，快 | 一次 LLM 摘要调用，慢 |
| 丢信息 | 少 | 多（摘要砍掉了细节） |
| 依赖 | **要视觉模型** | 任意模型 |

**一个反直觉的点**：soft 往往"省更多 token"，但那是**用丢信息换来的**。snapcompact 的卖点从来不是"比摘要更省"，而是"**接近逐字的保真度，代价是原文 1/3 的 token 价**"。benchmark 里 snapcompact 赢的是**保真度/token 价**，不是原始 token 减少量。

所以如果你发现 soft 省得更多——那是正常的，因为它顺手把旧信息的细节也扔了。你拿到"更省"的代价是"更丢"。

## 它省的是什么

**省的是 context window（token 预算），不是墙钟速度。**

这是理解 snapcompact 的关键。benchmark 量的是**输入 token 数（= 钱 / 窗口占用）**，**没量推理延迟，也没量缓存命中率**。所以"更省 token ≠ 更快"。

实测样本里，79946 字符若以原文文本存约 2 万+ token，压成 4 张图后只占几千 token——窗口腾出来了，长会话能撑更久。

## 它的独特设计（读源码看到的）

**1. 中央视觉 + 周边稀疏（foveated archive）**
和人类眼睛一样：历史最旧的一头、和刚进入文本区之前的一头，用**高清帧**（保真、易读）；中间最不重要的部分用**低清密排帧**——同样像素、同样计费，但切更小的字格，省 ~40% 字符空间。重要的地方看清、不重要的地方看不清就行。

**2. 面向不同 provider 的形状表**
不同模型的计费/视觉格不同，omp 为每个 provider family 选最优字形和帧尺寸：
- Anthropic：`11on16-bw`（1568px，原生视觉）
- Google / OpenAI：`8on22-bw`（加行距，行号更易读）
- 高分辨率档（Opus 4.7+/Fable/Mythos）：`1932px`，省约 1/3 帧数

**3. 惰性 blob 读取**
帧存成 `blob:sha256:` 引用，resume 时**不立即读**，只有到重建上下文时才**按预算只读最新的几张**（实测：10 张帧只读了 7 张，优先含最新的）。老帧继续当 blob 躺磁盘。

**4. 每请求预算封顶**
- 图像数预算：Anthropic 90、OpenAI/Google 200、未知 5（保守）
- 每请求 base64 总量上限 **3MB**——注释原话："模型名义上吃得起 70 张图，但每轮扛不住 ~11MB 的 JSON body"
- 超出就只挑最新的几张发，剩下的留磁盘等下次

**5. 崩溃安全**
某帧 blob 被删了，发送路径**宁可丢掉那张图**，也不会发一个悬空的 `blob:sha256:` 引用过去（否则后端收 body 但流式中 5xx）。

**6. CJK 支持**
中文字符重的文本会切到 `silver16` 字格，避免默认字体渲染不了宽字符。

## 它贵在哪里：缓存击穿（隐藏成本）

这是我认为最值得讲、而 benchmark 没算的一点。

snapcompact 把旧历史从**文本换成图片**，上下文内容变了——于是**前缀缓存（prompt cache）失效**。provider 的缓存按内容指纹匹配，文本→图指纹就不对了。结果：

1. **旧文本的缓存白存了**；
2. **下一轮要重发大 payload**（帧进请求体，上限 3MB）；
3. **视觉 token 要重新算**（比等效文本贵）。

叠加起来就是——**压缩后首次响应变慢**。

关键补充：这是**一次性的爆发**，不是每轮都慢。压缩后 `[摘要 + 帧]` 这段稳定下来，就成为可缓存前缀；之后每轮只重算末尾变化的最近原文，缓存回暖。所以是**每次压缩边界慢一次，之后回血**。

而且——**soft 也打爆缓存**（它的摘要同样替换了文本）。区别在于：soft 压缩动作本身多一次 LLM 调用（更慢），而 snapcompact 回血后 carry 的是**贵**的视觉 token，soft carry 的是**便宜**的散文文本。

一句话总结这个 irony：**snapcompact 用"缓存击穿"换了"窗口节省"**。它让钱包（token 数）省，但让第一次响应变慢。benchmark 只报了前者。

## 怎么选

| 你的瓶颈 | 选哪个 |
|---|---|
| **窗口太小**（超长会话、500k+、频繁触发压缩） | **snapcompact**——token savings 是硬需求，缓存击穿那一次慢可接受 |
| **在意交互延迟**（实时对话、频繁轮次） | **soft / 原生 server compaction**——缓存 warmed 后每轮更"跟手"，carry 便宜文本 |
| **模型没有视觉能力** | soft（snapcompact 要视觉模型） |

## 一句话收尾

snapcompact 是"用图片换窗口"的思路：按 ~1/3 token 价、逐字级保真地把历史存进上下文，让长会话撑得更久。但它省的是**窗口**，不是**速度**——代价是依赖视觉模型、且每次压缩会击穿前缀缓存让首响应慢一次。**更省 token ≠ 更快**，benchmark 报的是钱包，你测的是体验。选型取决于你卡的是窗口还是延迟。
