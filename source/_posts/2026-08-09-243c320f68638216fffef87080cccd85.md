## 1. 现状（源码证据）

### 1.1 裁剪：溢出后被动触发，两条路径预算不一致

两条路径**都只在 provider 返回 `context_window_exceeded` 之后才触发**，没有任何发送前预算检查：

- **A 路径**（`context_recovery.rs:59` `try_recover_context_overflow`）：
  预算 = **当前 token 的 2/3**（`context_recovery.rs:81`，`tokens_now.saturating_mul(2) / 3`）——不是按模型窗口留余量，是无差别砍三分之一。
- **B 路径**（交互式循环 `loop_.rs:2638`）：
  预算 = **配置窗口的 90%**（`eff_model_context_window * 9 / 10`，窗口值来自 `loop_.rs:1248` 的 `agent.resolved.model_context_window`）——数字上更合理，但仍是被动触发，且依赖 1.2 那个不真实的窗口数字。

两条路径的裁剪动作相同：整轮丢弃最老 turn（不拆 tool_use/tool_result 对）→ 插入 model-visible breadcrumb → 重试一次。长会话反复「溢出 → 砍 → 重试」。

### 1.2 窗口：32k 默认值，无模型真实窗口的自动解析

- `max_context_tokens` / `model_context_window` 默认值均为 **32_000**（`schema.rs:3535-3536`），未配置时的 fallback 常量同样是 32_000（`schema.rs:4692`）。
- provider 配置字段 `context_window` 已可读取（`effective_model_context_window`，`schema.rs:4198`）——B 路径的 90% 至少是配置过的数字；但手动不配，仍是 32k 硬顶。
- 自动 per-model `context_window` 解析（#7100 线：#9535/#9854/#9083/#8966）**截至 2026-08-31 全部 open 未合并**。runtime 对「模型窗口到底多大」仍没有可靠信息。
- 窗口数字本身不是模型事实，谈何用满。

### 1.3 缓存：仅 Anthropic 主动标记，runtime 无缓存友好约束

- Anthropic：system 前缀、最后一条消息、最后一个 tool 定义均标 `cache_control: ephemeral`（`anthropic.rs:358-421`）——provider 层照抄最佳实践，runtime 无参与。
- OpenAI：仅读取 `cached_tokens` 计费（`openai.rs:596`），客户端不标记（provider 自动缓存，合理）。
- Bedrock：`should_cache_system` 只在 system > 3072 token 时缓存。
- **核心冲突**：Anthropic 缓存是**前缀缓存**。每次溢出裁掉最老整轮 → 前缀变化 → 缓存全失效 → 重试 = 缓存重写 + 重试双倍成本。修剪越频繁，缓存命中率越低，甚至更贵。

### 1.4 根因：三块都为「单次请求正确性」兜底，无一块为「长会话连续性/经济性」负责

- 裁剪是 safety net（不崩、不产生幻觉替代物），设计输入里没有「利用率」「缓存命中率」。
- 窗口是配置默认值，不是模型事实。
- 缓存是 provider 自带的，runtime 无约束。
- #8196 砍掉 LLM summary 后，「确定性裁剪」成为唯一幸存者——最简单、最不易错，代价就是窗口空置 + 缓存自废。

## 3. 优化路线：以 omp 为已验证参考实现的移植路径

> omp 在 Pi 的 entry 投影模型之上，用 **StablePrefix + AppendOnlyLog + 常开轻 prune + 互斥重型策略** 重建了同一套问题，
> 核心洞察：**上下文管理 ≈ 缓存管理**。以下 R 项标注其对应的 omp 实现（详见参考 gist），ZeroClaw 无需重新设计，照搬 + Rust 化即可。

### R1（前置）：真实窗口解析落地 → omp：promotion / 恢复路径
- 合并 #7100 线的 per-model `context_window` 解析（#9535/#9854/#9083/#8966，截至 2026-08-31 全部 open），runtime 以此为准。
- 无真实窗口，后续预算优化都在错误数字上做文章。

### R2：缓存经济学基建：稳定前缀 + 追加日志 → omp：StablePrefix / AppendOnlyLog
- **StablePrefix**（`append-only-context.ts`）：system prompt + 工具规格只计算一次并冻结，跨轮字节完全相同；仅 MCP 重连等事件 `invalidate()` 重建。
- **AppendOnlyLog**：消息只增不改，唯一改写口 `replaceTail()` 预留给压缩。
- 直接替代 P4 的根因：现在的「砍最老整轮」是前缀删除，反着来的。

### R3：发送前预算 + 多相位触发 → omp：多相位触发
- omp 触发时机：每轮 stale prune（无条件）→ 条件年龄 prune → pre-prompt / mid-turn / post-agent-end 阈值检查；handoff 策略 post-turn **defer**、mid-turn **suppress**；overflow / incomplete 恢复路径**强制 inline**。
- 替代现在的「只等溢出错误」：每轮先跑轻 prune，压缩时机按相位与策略分派，而不是一刀切。

### R4：工具结果分类管理 → omp：工具结果语义分级
- **受保护工具**（protectedTools：`skill`、plan 文件 read）、**超驰**（同一文件多次 read 只留最新）、**useless 剔除**（工具自标，如零匹配 grep）。
- 替代 P5 的「无分类」：让大块 tool_result 在入上下文前就有分级处置。

### R5：缓存友好的「多道闸」修剪 → omp：温区守卫 + idle 冷窗 + boundary + minimumSavings
- **后缀温区守卫（~8k）**：埋在已发送缓存深处的消息，改写 = 重写整段后缀（cacheWrite 溢价），跳过。
- **idle 冷窗（90min）**：深度清理只在缓存已冷（TTL 1h 过后）才做，重写免费。
- **compaction boundary**：已压缩掉的消息跳过，mutate 纯浪费。
- **收益门槛**：省不够阈值不动手，防「为省 1 token 重写一遍缓存」。
- 这四道闸直接回应 P4：每轮跑 ≠ 每轮改，多数轮次零 mutation、零缓存失效。

### R6：统一预算管线（架构层）
- 三块代码（history_trim / context_recovery / provider cache 标记）收敛为单一 `ContextBudget` 层：输入窗口（R1）、system floor、工具定义、缓存断点、历史；输出「该不该裁、裁到哪个边界、走哪条策略通道」。
- omp 的形态可作参照：`compaction/` 子系统 + `append-only-context.ts` + `session-maintenance.ts` 编排层。

### R7（可选，经济性闭环）
- 按轮记录 `cache_read_input_tokens` / `cache_creation_input_tokens`，出命中率报表验证 R2/R5 效果。

## 4. 移植风险与权衡

- **语言差异**：omp 是 TS 编排层（Rust 内核），ZeroClaw 全 Rust。StablePrefix/AppendOnlyLog/多相位触发均可直接移植为 Rust 结构；omp 的「每轮扫 session entries」廉价性在 Rust 下只会更好。
- **provider 缓存模型**：Anthropic 前缀缓存（cacheWrite 溢价）是 omp 经济学的核心假设，ZeroClaw 主要 provider 一致；OpenAI 靠自动缓存（只读计费），Bedrock 有 system 阈值——差异策略仍按每家对齐，但主干机制（稳定前缀）与 provider 无关、通用。
- **omp 的边界（已知空位）**：omp 明确**不做**「按信息价值取舍」的语义层——价值场景相关、无法预测，语义分级要么靠用户输入（可见性 + 心智负担两难），要么引入不可预测性。ZeroClaw 若想超越 omp，可考虑这层（用户侧「这条保留」的显式标记），但这不是移植阻点，而是后续增量。
- **回归风险**：R2 的前缀冻结要求 system/tools 序列化确定性；MCP 工具集动态变化时需显式 invalidate 路径（omp 已处理）。

## 5. 一句话总结

> ZeroClaw 现状：溢出 → 被动砍最老整轮（两条路径：当前 token 的 2/3 / 配置窗口的 90%）→ 重试，窗口 32k 默认顶没用满，前缀裁剪自废缓存。
> 正确路径不是重新发明，而是**移植 omp 已验证机制**：稳定前缀 + 追加日志（R2）→ 发送前多相位触发（R3）→ 工具结果分类（R4）→ 缓存多道闸修剪（R5）→ 统一预算管线（R6），前置仍是真实窗口解析（R1）。
> 若要比 omp 更进一步，唯一空位是「按价值取舍」的语义层（omp 明确放弃的位置）。
