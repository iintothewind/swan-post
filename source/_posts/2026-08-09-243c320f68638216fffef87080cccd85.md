# ZeroClaw 上下文管理现状分析与优化路线（RFC 草稿 v2）

> **v2 复核**：2026-09-09 @ **zerolite `ac36fd0e2`**。v1 复核的是 2026-08-31 的 master（`4b73b37`），
> zerolite 已把 v1 的多项「现状」与「待办」变成既成事实——**v1 的 1.1 / 1.2 / P1 / P3 / R1 / R7 对 zerolite 已过时**，本版逐条重述并附 HEAD 上的源码证据。
> 参考实现仍是 omp（`can1357/oh-my-pi`），但本版的核心修正是：**omp 的条目级修剪模型与 zerolite 的头部整轮截断模型不兼容，R4/R5 的移植前提不成立**，
> 真正的剩余优化在别处（见第 5 节 ROI 排序）。

## 1. 现状（zerolite `ac36fd0e2` 源码证据）

### 1.1 裁剪：已是发送前预算 + 单内核，动作是「整轮截断到低水位」

- 单一决策内核 `plan_pre_send_trim`（`turn/context_pipeline.rs`）：三条路径（轮界预防、reported-budget enforce、溢出恢复）共用，v1 时代「三处各自推导、语义漂移」已不存在。
- token 计数已用 provider 权威值锚定：`ContextCalibration`（`history_trim.rs`）以 provider 报告的 prompt 大小为锚，本地启发式只为「已 append 未计费尾部」补价——omp `calculateContextTokens` 的 Rust 等价物。
- 溢出恢复保留唯一的更激进档：强制收缩到当前 2/3（`plan_pre_send_trim` 的 `forced_shrink`），语义正确——provider 已拒绝，next-fit 到预算线不够深。
- **裁剪动作 = `trim_to_recent_turns`：只保留最近 N 个完整 turn**（默认 5，clamp 1..10），不看裁后 token 数。这是**有意的低水位设计**，理由见 1.3。

### 1.2 窗口：per-model 解析已落地（v1 的 P3 关闭）

三级链（`schema.rs:4222` `effective_model_context_window`）：
1. 显式 provider `context_window`（config）永远优先；
2. 本地表 `context_window.rs::MODEL_CONTEXT_WINDOWS`：按归一化 model id 最长前缀匹配，记录的是**保守下界**（同族取最窄可得值）；
3. `UNCONFIGURED_CONTEXT_WINDOW_FALLBACK = 32_000`（`schema.rs:4721`）仅作最后兜底。

v1 追的 #7100 线四个 PR 不再是 zerolite 的前置依赖。

### 1.3 缓存：追加日志已接线，头部截断的经济学已经自洽

- **`AppendOnlyLog` 已接入主 loop**（`turn/mod.rs` 的 `provider_log`）：按**位置**存 FNV-1a digest，`sync` 保最长字节稳定前缀；列表变短（= 任何裁剪/压缩）直接 `clear()` 重建（`log.rs:100-117`）。
- 这条实现细节就是设计依据的物证：**头部删一条，`messages[0]` 的 digest 立刻对不上，稳定前缀归零——任何头部删除都要为剩余后缀付一次完整 cacheWrite**。「少删点」不「少付点」。
- 因此 **v1 设想的浅裁高频触发是纯亏**：对几乎不变大的后缀反复重写。zerolite 收敛到「单高水位触发、一次深裁到 keep_recent_turns」是**该模型下的正确终态**：一次重写换 K 轮便宜追加。
- Anthropic 标记照旧：system 块 / tools / 最后一条消息 `cache_control: ephemeral`（`anthropic.rs:620,632,1406` 等）。**`CacheControl` 无 `ttl` 字段 → 全程默认 5 分钟 ephemeral**，1 小时扩展缓存未使用。
- **`StablePrefix`（`prefix.rs`）未接线**：机制完整（指纹冻结 / `invalidate` / version 计数 / 所有权断开），runtime 零调用点。见 R2。

### 1.4 根因更新：v1 的三块里两块已经有人负责了

- 「裁剪只为单次正确性兜底」不再成立：现在有发送前预算、有 provider 权威计数、裁剪深度有缓存经济学理由。
- 「窗口是配置默认值不是模型事实」不再成立。
- **仍然成立的一条：头部字节每轮被原地重建**。`sys_msg.content = build_system_prompt_for_turn(...)` 在每个 iteration 里执行（`loop_.rs:1909`、`2466` 两处）。它抖不抖取决于重建输入（见 R2 的漂移源清单）。

## 3. 路线项状态（v2）

### R1：真实窗口解析 — ✅ 已落地
见 1.2。v1 本节及其对 1.2 的批评删除。

### R2：稳定前缀 + 追加日志 — ◐ 半落地，收尾是**有条件项**
- AppendOnlyLog 已接线；StablePrefix 未接线。
- StablePrefix 不增加缓存覆盖面（history 增量靠 Anthropic 断点自动走），它唯一的事是**保证/暴露头部字节跨轮不变**。接线本身不产生收益：若头部每轮合法地变，接上去只会如实记录 `version++`。
- **头部漂移源清单（实测）**：
  - 日期：`## Current Date` 是 `%Y-%m-%d` **天级**（`system_prompt.rs:455-459`）→ 日内稳定，跨午夜抖一次。
  - `tool_filter_groups` dynamic 模式：MCP 工具集**按当条消息关键词**过滤，同时喂 system prompt 工具段与 provider tool specs（`loop_.rs:419-439,489`）→ 配了它的会话前缀每轮买断。**这是显式 opt-in、默认空**（`schema.rs:5916-5927,3604`），本意是「没命中的轮次少付几万 token 的 MCP 定义费」换「翻转轮重写前缀（1.25x）」——对挂着大 MCP 的用户是划算的取舍，不是无收益设计；缺的是文档写明它烧前缀缓存。
  - MCP 重连 / skill 激活 / 模型切换：**该** invalidate 的合法事件。
  - （**推断，未核**）deferred tool 激活（`ActivatedToolSet` 进 tool specs）是否在中途改变工具段字节 → 激活轮的前缀买断。
- **结论**：接线前先答「你的部署配 `tool_filter_groups` 吗 / R7 数据显示头部每轮买断吗」，否则优先级低。

### R3：发送前预算 + 多相位触发 — ✅ 实质落地
单内核 + provider 权威计数 + 溢出强制深裁。omp 的 mid-turn / post-agent-end 分相在头部截断模型下增益很小：越线即裁没有「挑时机」余地，未采。**结案，不再追。**

### R4：工具结果分类 — **降级为「入口时子集」，sidecar map 设计整体推迟**
- v1 设计纪要（`Map<tool_call_id, MessageClass>`、四条硬不变量）**存档不实施**。理由：map 的存在理由是**事后 trim 侧消费者**（按 class 豁免/挑选），而当前 trim 是整轮保留、"never cut a turn in half"，**protectedTools 没有消费者**；且 skill 内容在 system prompt（稳定前缀）里，protected 的对象本身所剩无几。
- 有价值的子集是**入口时**的 supersede（同文件重复 read 留最新）与 useless 剔除（零匹配 grep→stub）：两者都在 append 边界决策，而 name/args 在 `results_collect.rs` **本来就在作用域**——把 name 带进 `append_tool_round_to_history` 即可，零 sidecar、零对齐不变量、零缓存代价（消息未入历史，谈不上污染前缀）。
- 入口处已有无差别的 `max_tool_result_chars` 截断兜底单条体积；子集收益取决于「重复 read / 空结果在真实会话的 token 占比」——**先测量再动手**（第 5 节 #5）。
- 复活条件：条目级修剪立项的那天，map 与其四条不变量按 v1 纪要原样启用（分类规则与载体分离的设计保留）。

### R5：多道闸修剪 — **对当前模型重分类：四道闸三道空转**

| 闸 | 在头部整轮截断模型下 |
|---|---------------------|
| 温区守卫（不动最近 ~8k） | **空转**——只删头部，天然不碰尾部 |
| compaction boundary | **空转**——#8196 后无 compaction |
| minimumSavings | **空转**——越线必须立刻裁，无「省不够不动手」选项 |
| idle 冷窗（90min） | 唯一勉强成立，但 zerolite 的 TTL 是**默认 5 分钟**（无 `ttl` 字段），omp 的 90 分钟是按 1h 扩展缓存算的；5 分钟下缓存本就冷得频繁，且代价反向：深裁那一次经常**热着**付费 |

**结论修正**：v1 说「R4 不落地 ⇒ R5 依赖未满足」——更准确的是 **R5 是条目级修剪（改中间某条）的配套装置**（管「改太贵，挑便宜时机改」），zeroclaw 的动作是头部整体截断，不存在「便宜时机」。此前 coding agent 半程后长成原管线补丁，**是架构模型不匹配的必然，不是执行质量问题**。条目级修剪立项之日 R5 随其复活，届时含：wire bytes 级前缀对齐（任何中间删除改写其后全部字节，`log.rs` 只是如实反映）、TTL 感知的改写时机。

### R6：统一预算管线 — ◐ 已实质大半
`context_pipeline.rs` 单内核 + `zeroclaw-context` 独立 crate（机制与策略分离、可单测）已是该管线的雏形。剩余（provider cache 标记收编）收益低，不排期。

### R7：命中率报表 — ✅ 采集链已存在（v1 高估了工作量）
- OpenAI 兼容（含 vLLM）：`prompt_tokens_details.cached_tokens` → `cached_input_tokens`（`openai.rs:612,698`）；**vLLM 侧需 `--enable-prompt-tokens-details` 启动**，否则整个 details 缺席。
- Anthropic：`cache_read_input_tokens` → `cached_input_tokens`（`anthropic.rs:1846`）。
- 下游：`cost.rs` 按 `cached_rate` 折扣计费；OTel 属性 `zeroclaw.usage.cached_input_tokens`（`otel.rs:644`）；Prometheus **`zeroclaw_tokens_cached_input_total{model_provider,model}`**（`prometheus.rs:87`，注释明确与 response cache 分开）。
- **命中率报表 = PromQL 面板，不是代码**：`rate(zeroclaw_tokens_cached_input_total) / rate(tokens_input_total)` 按 model 分组。

## 4. 移植风险与权衡（v2 修订）

- 语言差异一条保留（结论不变：机制可移植，Rust 下更便宜）。
- provider 缓存模型一条**加重要限定**：omp 经济学的 idle/冷窗假设按 1h 扩展缓存定价；zerolite 固定 5 分钟 TTL，同一套闸门的时间常数全部失效。移植任何「挑时机改写」机制前，先决定是否给 `CacheControl` 加 `ttl`。
- 「语义层是 omp 空位」一条保留，但挂在条目级模型立项之后才有意义。
- 新增回归面备忘：`tool_filter_groups` 的行为若为缓存稳定性而改（如改 per-session sticky），会改变「按轮少付 MCP token」的成本结构，须带着 P6 修复后的三档计费重估。

## 5. 高 ROI 待办（按性价比排序，2026-09-09）

1. **P6 修复：`cache_creation_input_tokens` 透传 + 三档计费**。`TokenUsage` 加字段（`anthropic.rs` 映射处已有现成变量），`cost.rs` 加 write 档（1.25x）。改动最小，且它是后面每一项的**计量地基**——不修，前缀重写的代价在账本上永远是零。
2. **PromQL 命中率面板（零代码）**。回答三个悬案：web 聊天前缀跨轮真实命中率；深裁一次重写有多贵；5 分钟 TTL 下热态实际存活率。所有后续决策的读数来源。
3. **TTL 决策**（依赖 #2 数据）：`CacheControl` 加 `ttl`，评估 1h 扩展缓存（写入 2x、读 0.1x 的定价）对聊天节奏是否翻本。数据前不动。
4. **StablePrefix 接线**（依赖 #2 显示头部确实每轮买断，且先裁决 `tool_filter_groups` / deferred 激活两个漂移源）。裁决方向：per-message 工具过滤改成缓存中性做法，或书面承认它是按轮买断的 opt-in 特性（补文档）。
5. **工具结果入口时子集**（依赖测量）：带 name 进 append 边界，supersede + 空结果 stub，几十行；触发条件 = #2/#7 数据显示重复 read/空结果占比可观。sidecar map **不做**。
6. **P2 残余（轮粒度）不动**：唯一解是轮内压缩（需要被 #8196 砍掉的 summary 层），记录为开放问题，不排期。

**明确不做**：R4 全量 sidecar 设计；token 低水位线（与轮数低水位语义重叠且受同一粒度约束，退不回比 1 轮更浅）；R5 在当前模型上的任何 retrofit；为 `tool_filter_groups` 缓存问题而移除 MCP（该路径对未配置用户根本不存在）。

## 6. 一句话总结

> zerolite 现状：per-model 窗口 ✅、发送前单内核预算 ✅、追加日志 ✅、深裁低水位（模型内自洽）✅。
> v1 路线里 R3/R7 已经做掉，R1 已做掉；R4 降级为入口时子集（先测量），R5 随条目级模型立项才有意义，StablePrefix 接线取决于头部漂移是否真实存在。
> 当前最高回报的动作不是任何上下文策略，而是**把 cacheWrite 的 1.25x 记进账本（P6）**，然后用一个 PromQL 面板让数据决定下一个动谁。
