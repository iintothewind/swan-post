# Rentry.co API Research — 补充 Claim 机制与所有权分析

> 验证日期：2026-07-23 | 验证人：Zero | 含两次补充

---

## 概览

Rentry.co 是一个零注册、零配置的 markdown 便签 / pastebin 服务。
提供 CSV 免保护的 REST API，只需 curl + POST 即可完成全部操作。

**适合场景：** 临时分享 markdown 内容、发日志、写小文档、AI agent 往外部写结果。

---

## API 端点

所有端点均为 `POST`，CSRF 免保护，仅限 `application/x-www-form-urlencoded`。

### 1. 新建 — `POST /api/new`

```bash
curl -X POST https://rentry.co/api/new \
  -d "text=# Hello World%0A%0AMarkdown 正文"
```

**Response:**
```json
{
  "status": "200",
  "content": "OK",
  "url": "https://rentry.co/abcdef12",
  "url_short": "abcdef12",
  "edit_code": "A1b2C3d4"
}
```

**要点：**
- 返回 `edit_code` — **这是后面编辑/删除/读取的唯一凭证，必须存好**
- URL 短码随机生成，不可自定义
- 标题不含 `%0A` escape — 实测直接用 `\n` 也可以 curl 的 `-d` 解析

### 2. 编辑 — `POST /api/edit/[url]`

```bash
curl -X POST https://rentry.co/api/edit/abcdef12 \
  -d "edit_code=A1b2C3d4&text=新内容"
```

**Response:**
```json
{"status": "200", "content": "OK"}
```

### 3. 读取内容 — `POST /api/fetch/[url]`

```bash
curl -X POST https://rentry.co/api/fetch/abcdef12 \
  -d "edit_code=A1b2C3d4"
```

**Response:**
```json
{
  "status": "200",
  "content": {
    "url": "abcdef12",
    "views": 0,
    "pub_date": "2026-07-23T21:59:58+00:00",
    "edit_date": null,
    "text": "# Hello World\n\nMarkdown 正文",
    "metadata": null,
    "metadata_version": null
  }
}
```

### 4. 删除 — `POST /api/delete/[url]`

```bash
curl -X POST https://rentry.co/api/delete/abcdef12 \
  -d "edit_code=A1b2C3d4"
```

**Response:**
```json
{"status": "200", "content": "OK"}
```

### 5. 读取 RAW — `POST /api/raw/[url]`

```bash
curl https://rentry.co/api/raw/abcdef12
```

**⚠️ 注意：** 需要管理员设置的 `SECRET_RAW_ACCESS_CODE`，普通用户不可用。返回 `403`。

### 6. 网页端

`GET https://rentry.co/[url]` — 渲染后的 markdown 页面，正常 HTTP 200。
可用 Jina Reader 等工具抓取纯文本。

## 登录系统与 Claim 机制（⚠️ 核心补充）

### 登录系统

Rentry 确实有登录系统：`/request-login` — 输邮箱收 magic link，无需密码。
此外还有会员订阅：`/user-account/membership`。

**但 API 层面完全不依赖登录** — 创建、编辑、删除、读取全部靠 `edit_code` 完成，没有任何需要 token/cookie 的 API 端点。

### Claim 系统（URL 所有权转移）

`/request-url` 表单提供一套**人工审核的 URL 过户机制**，与 edit_code 是**两套独立系统**：

| 机制 | 凭证 | 方式 | 审核 |
|------|------|------|------|
| 正常编辑 | `edit_code` | 直接 API 调用 | 无，有 code 即可 |
| Claim 过户 | 邮箱验证 | 提交表单 → 管理员审核 | 人工审核 |

**Claim 不是**「凭 edit_code 获取权限」— 它是向管理员申请将一个 URL 的所有权（即 edit_code 控制权）转移给你，与原有 edit_code 无关。

### 所有权保护规则

来源：[claim-guide](https://rentry.co/claim-guide)

| 条件 | 保护状态 |
|------|----------|
| 创建后 **12 个月内** | ✅ 完全安全，不可 claim |
| 每年至少编辑一次 + 有真实内容 | ✅ 无限期安全 |
| 超过 12 个月没编辑 | ⚠️ 可被 claim（管理员审核） |
| 通过 claim 获得的 URL | ⚠️ 仅 3 个月保护期，期满可被 reclaim |
| 无真实内容（囤积 URL） | ❌ 随时可能被回收 |

**真实内容定义：** 人为创建、至少 30 秒编辑投入的内容。纯链接列表、占位符、WIP 标记不算。

### 真正的所有权风险排序

1. **🔴 edit_code 泄露** — 任何人只要有 code 就能直接编辑/删除你的帖子，无审核，无挽回
2. **🟡 弱 edit_code** — 自定义短 code（如 `123`）可被暴力枚举
3. **🟢 被 claim** — 需走表单 + 人工审核，门槛高，且编辑活跃的真实内容几乎不会被批准
4. **⚪ 忘记 edit_code** — 可通过邮箱联系客服验证身份找回（需有 claim 记录）

### 核心结论

- **默认帖子所有权靠 `edit_code` 维系**，与账号无关
- 登录账号的主要用途是做 **claim（URL 过户申请）** + 找回 edit_code
- 对正常用户（有强 edit_code + 定期编辑 + 真实内容）来说，帖子实际上是安全的
- Claim 系统主要针对 **URL 囤积者**（占着常见词但不放内容的人），而非普通用户
- **真正的威胁不是 claim，而是 edit_code 泄露或丢失**

## 注意事项

### 凭证

- **`edit_code` 是唯一的写凭据**，服务端不存邮箱、密码、session。
- 创建后如果丢了 `edit_code`，**永远无法编辑/删除**（除非有 claim 记录可找客服）。
- 建议：创建后立即存本地，或设计成 user 提供 edit_code 才可编辑。

### 已知限制

| 限制项 | 值 |
|--------|-----|
| 编辑次数 | 每次编辑后最多再改 10 次（由服务端 `modifications_left` 控制？未详细测试） |
| 速率限制 | ~10 次/分/IP（Cloudflare 层面，超出返回 429/403） |
| URL 自定义 | ❌ 不可自定义短码 |
| 元数据 | API 返回 metadata 字段但始终为 null（未开放） |
| Auth | 无 token/API key，对 edit_code 暴力破解理论上可行，但短码+edit_code 组合空间足够大 |
| `\n` vs `%0A` | curl `-d` 参数用 `&text=...` 时，里面可以直接用 `\n` 换行，但 shell 里注意引号 |

### 数据持久性

未找到官方承诺的保留期。按 pastebin 类服务惯例，长期不访问的内容可能被清理。
**不适合长期重要文档。**

## Skill 设计建议

### 典型命令

```bash
bash rentry.sh new  /path/to/file.md           # 新建，输出 url + edit_code
bash rentry.sh edit <url> <edit_code> <file>   # 编辑已有内容
bash rentry.sh fetch <url> <edit_code>          # 读取内容
bash rentry.sh delete <url> <edit_code>         # 删除
```

### 本地 edit_code 管理

方案一：创建时在本地 `~/.rentry_codes` 做 kv 缓存（`url = edit_code`），fetch/edit/delete 自动匹配。
方案二：skill 不存，让调用者传参（更透明，但责任转移）。

建议方案一（缓存）对用户透明；但技能说明里必须强调 edit_code 的重要性。

### 使用模式

- AI agent 把 markdown 报告发到 rentry → 输出 URL 给用户 → 用户浏览器看
- 用户写好 md → agent 上传 → 返回 URL
- 临时日志分享 / 调试输出
