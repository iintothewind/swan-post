# Domain-Driven Agents — 简述与评论

URL: https://coldtake.dev/blog/domain-driven-agents

## 文章简述

作者核心论点：AI agent 在绿地项目好用，在 legacy（重耦合、技术债、设计漂移）代码库里产出骤降。失败有固定形状——模型在已有多个拼写的领域概念上发明新的、该写 adapter 处直连、该直连处写 adapter，因为每个问题「系统本身从没在任何地方回答过」，模型只能猜且常猜错。

归因：掉进去的不是模型，是代码库第二层——语义混乱、缺共享语言。模型不用升级，是 code is not ready，而 readiness 可增量构建。

方法：借用 Ousterhout 的 tactical/strategic，但按作者身份切——strategic=决策（读系统、定改什么/为何），tactical=把决策落到文件。判断：typing it out 成本崩塌，deciding 没降价。作者自己做 strategic 产 GitHub issue，tactical 交给 AI system 基于 skills（程序化 markdown 指令）+ sub-agents（独立 session、窄任务），自己当 reviewer。

DDD 作为地基：strategic 半价值取决于其语言质量。给出 context map + glossary：每个边界上下文声明自身语言，跨边界用 published-language / conformist / anticorruption-layer 标注；每条边界两边各声明一次，generator 交叉校验，不一致报 finding（带 fingerprint 去重、自动开关 issue）。真正的逐上下文迁移到真 domain 模型被推迟到「next post」。

## 我的评论（整理）

1. 根因被误名。文章把「代码库没准备好」当根因，实际根因是老系统随迭代设计不断漂移、领域概念充满矛盾、与最初设计偏离越来越大。「not ready」只是把症状命名成根因，真正的机制是设计漂移。

2. DDD 并非解决之 key。目标是搞定屎山，重新 DDD 没用——文章自己承认 context 内部仍是普通代码、能造 nonsense 对象并保存。它给的是边界层的护栏与导航，不是解药；真正的 domain 迁移被推迟到了下一篇，而那部分恰恰是贵、且作者承认战略半没降价的。

3. 整体只是重新解读。DDD 二十年前就讲过设计漂移与缺语言，并不新。文章真正新增的仅是：把它专门用来防止 agent 把屎山搞得更屎，并落成可操作物（skills 文件、sub-agent、fingerprinted findings、双边声明配对校验）。这是一篇工作流想法，不是工具，且零度量验证。

结论：它不是 solution，而是给「带 agent 进老仓库」这事儿的一层防呆 + 脚手架。要的是让屎山变好，它给的是让屎山在清理过程中别继续腐烂。两件事，别被标题骗成一件事。
